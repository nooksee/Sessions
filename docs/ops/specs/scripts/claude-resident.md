## First Principles Rationale

Claude Code chooses its automatic memory (the notebook) by Git root, so every resident who shares a repository shares one notebook, and a notebook gives a reader a name and a posture before any registry check. The design gives each Claude resident one notebook of its own, bound to its registry key, and a launch wrapper that attaches it only when the launch names exactly one registered Claude session. Every other launch in this room, apart from a registered row not yet wired (below), runs with auto memory off: nobody is handed anyone's notebook while unverified. The wrapper never blocks a launch; it only decides what the launch carries.

A Claude row registered to another room is verified too, by the same registry, as that room's resident; its present notebook is the provider's default for its own room, and this wrapper has no say over other rooms, so its launch passes through untouched (the Session Continuity Manager's decision, 2026-11-05).

A Claude row of this room that is not on the wired list passes through untouched as well, until its own go, so that the launch setting can go live with nobody wired and one resident can be accepted before the next (PoT 6.1.6; the Session Continuity Manager's ruling, 2026-11-07).

A launch whose working directory is outside this room passes through untouched too, before the registry is read. The launch setting that would reach this wrapper is host-wide, and this wrapper has no say over another room's conversations, new or named (the Session Continuity Manager's disposition of the Auditor's finding, 2026-11-05).

The decided home is one folder per registry key under `<room>/ops/etc/notebooks/`, mode 0700, out of Git (PR #14). The mind tool projects the current leaf into that folder's `MEMORY.md`, seals the folder at seams and restores it from a seal (`docs/ops/specs/scripts/mind.md`). This wrapper is the third duty: choosing, at launch, which notebook a run gets.

## Mechanics and Sequencing

**Forms.** There are three.
- **Dry run:** `claude-resident --dry-run [--room DIR] [--registry FILE] [--provider FILE] -- <provider arguments>`. `--dry-run` is the first argument. It prints the decision, executes nothing and writes nothing.
- **Explicit:** `claude-resident [--room DIR] [--registry FILE] [--provider FILE] -- <provider arguments>`. Options come before `--`, and every argument after `--` belongs to the provider, a later `--` included.
- **Bare:** `claude-resident <provider arguments>`, how a launcher calls a provider. It is recognized when there are no arguments at all, which is how the plugin's terminal action starts a provider, or when the first argument is neither one of the wrapper's option names (`--dry-run`, `--room`, `--registry`, `--provider`) nor `--`. It takes no options, the defaults apply, and every argument belongs to the provider, a later `--` included.

A first argument that is a wrapper option in a malformed list is refused with exit 2 and a usage line on standard error that echoes no argument. `--room` defaults to the room that holds the wrapper; `--registry` defaults to `<room>/ops/etc/resident-identities.json`. A relative option value under a working directory that is gone is refused the same way. The interpreter is Python 3 started with `-I -B` through `/usr/bin/env -S`; the wrapper uses the standard library and the room's mind tool.

**The decision, in order.**
1. **The working directory.** The kernel's resolved working directory decides, against the resolved room. Equal to the room or below it counts as in the room; a folder whose name merely begins with the room's does not. Outside it, the branch is **outside the room**: the launch passes through untouched, with no environment change and no notebook, before the registry is read. Three cases fail closed to auto memory off, the **working directory** branch: the directory is absent or cannot be reached; this user cannot read and enter it; or it is a link through the room that resolves elsewhere. That last can be seen only through `PWD`: `PWD` is absolute, names this same directory, one of its parent paths resolves into the room, and the resolved path is outside. `PWD` is read for nothing else and can only turn auto memory off. A stale, relative or absent `PWD` is ignored, and a link anywhere that resolves into the room counts as in the room.
2. **The registry.** It must be a regular file (not a link), owned by this user, at mode 0600, at most 1 MiB, read without following a link, UTF-8 JSON with an `identities` list. Every row must carry a non-empty string key, provider, session and room; every key must be a plain registry key (`^[a-z0-9][a-z0-9-]*\Z`, so no trailing newline); no key may appear in two rows. Any failure is the **broken registry** branch, whatever the arguments say, so a broken registry shows on every launch in this room.
3. **The session named.** The provider's arguments are scanned up to the provider's own `--`: `--resume <id>`, `--resume=<id>`, `-r <id>`, `--session-id <id>` and `--session-id=<id>` name a session. A flag with no value (the next argument absent or starting with `-`), `-c` or `--continue`, or no such flag at all names none; `--fork-session` gives the run a new session. Each of these is the **new** branch. Two different sessions named is the **ambiguous** branch; the same session named twice is one.
4. **The row.** The Claude rows (provider `claude`) whose session equals the one named: none is the **unregistered** branch (a row of another provider does not count); more than one is the **ambiguous** branch; exactly one is the **registered** candidate.
5. **The room.** If the candidate's room resolves to another room, the branch is **registered elsewhere**: the launch passes through untouched, with no environment change, no notebook attached and auto memory left as the provider's default for that room.
6. **The wired list.** `<room>/ops/etc/notebook-wired.json`, read only for a candidate of this room. No file means nobody is wired, and an empty list wires nobody. Otherwise it must be a regular file (not a link), owned by this user, at mode 0600, with one link, at most 64 KiB, read without following a link, UTF-8 JSON, a list of distinct strings, each the key of a Claude row of this room. Any failure is the **broken wired list** branch: auto memory off with a fixed reason, and the row's key in the log. No other branch reads the list, so it reaches no launch that does not name a row of this room. A candidate not on the list is the **registered unwired** branch: the launch passes through untouched. That is decided before the mind tool loads, so a fault in that tool cannot reach it.
7. **The notebook.** For a candidate on the list, its folder `<room>/ops/etc/notebooks/<key>/` must pass the mind tool's private-path rules (every component present and none a link; this user's folder at 0700; an existing `MEMORY.md` this user's single-link regular file at 0600) and the mind tool's Git rule (outside Git, or ignored by the nearest repository). Every projection marker in its `MEMORY.md` must be a well-formed marker of this key, so a folder holding another key's projection is never attached. A launch whose own arguments, up to the provider's `--`, already carry `--settings` or `--settings=` cannot take the route (see limits). When all of that holds, the branch is **registered** and the notebook is attached; when any of it fails, the branch stays **registered** but nothing is attached and auto memory is off, with the reason.

**What a run carries.** The attached branch adds one thing, the route, and no environment change: `--settings <room>/logs/claude-resident/<key>.settings.json` placed before the provider's arguments. That file holds one key, `autoMemoryDirectory`, naming the folder. The provider's installed schema and its memory documentation both give this as the way to choose the folder, and read it from `--settings`; the value must be an absolute path, which it always is here. That the installed provider then uses it is a native proof (below). The registered-elsewhere, registered-unwired and outside-the-room branches add nothing at all: the provider's environment and arguments are byte for byte what the wrapper was given. Every other outcome sets `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, over any inherited value, and attaches nothing. An unexpected error anywhere in the decision, the mind tool exiting as it loads included, is the **error** outcome, handled the same way: auto memory off, nothing attached, the launch not blocked.

**The settings file.** One file per key. The folder is made at 0700 if absent, and must pass the mind tool's private-path and Git rules. Two first launches can meet there: the second finds it made, checks it and goes on. The file is 0600, single-link and replaced atomically, and only when its bytes, its mode or its link count differ, so a launch adds nothing there: the exec leaves nothing behind that could clean up after it. It lives under `logs/`, where this room keeps tool state, and not under `var/tmp`, which is scratch (PoT 1.1.13). If the folder or the file is in doubt, or the write fails, nothing is attached and auto memory is off; the launch still runs. The decision checks that place read-only, so the dry run gives the same answer the launch would, and the launch checks it again just before it writes.

**The decision log.** Every real launch appends one JSON line to `<room>/logs/claude-resident/decisions.log`, before the exec, so a notebook lost at a launch can be seen afterwards. The fields: `time` (UTC); `branch`; `notebook` (`attached` or `none`, as the launch went, so a route lost at the write reads `none`); `memory_off` (whether the run's environment holds the switch at 1, an inherited one included); `reason` (the dry run's fixed text); `key`; and `provider` (`found`, `none`, or `could not be executed`, which adds a second line). `key` is the registry key of a row of this room and null otherwise, and it is the only identifier: no session, argument, room, person, role or working directory is written. The file is 0600 and single-link in the settings folder, under the same place rules and out of Git. It turns over at 1 MiB to one earlier file, `decisions.log.1`, so the log is at most two files; two launches at the turn can lose the earlier one, because the log is a record of decisions and not custody. The earlier file answers to the same place rules: if its name cannot be placed, the log does not turn over and that launch gets no line. A loose mode is tightened; a link, a pipe, a folder, a second hard link or another owner's file gets no line. Nothing about the log can stop or change a launch. The dry run writes no line.

**The exec.** The real forms replace the wrapper's process with the provider, so the arguments, the standard streams, the working directory, the umask and the exit status are the provider's own. So is the environment: Python sets `LC_CTYPE` at start under a C locale (PEP 538), which `-I` does not stop, so the wrapper returns that one variable to what the kernel's copy of its environment holds. Three things do not pass through, and no real launch is known to carry them: an entry with no `=` does not survive Python's reading; duplicate entries collapse to the first; and an entry with an empty name is dropped, because `execve` refuses it and a direct start would run. A parent's ignored SIGPIPE or SIGXFSZ is not preserved either: both go to their defaults, below. The wrapper writes nothing to standard output. SIGPIPE and SIGXFSZ are restored to their defaults first, because Python ignores them at start and an ignored signal survives an exec, which every command the provider runs would inherit. If the exec fails they are ignored again, since the launch stays in the wrapper and a write limit must not kill it before its message and its second log line. The provider is the file `--provider` names, or the first `claude` on PATH, skipping empty and relative PATH entries, which would run whatever the working directory holds, and never this wrapper itself, so a launcher can never loop. With no provider the wrapper states so on standard error and exits 127; with one that cannot be executed, 126. Those are the only ways it can fail a launch, and neither echoes an argument. Both statuses come through with no reader on standard error.

**Dry-run output.** One JSON object on standard output, with sorted keys: `mode` (`dry-run`), `executed` (`false`), `branch`, `notebook` (`attached` or `none`), `auto_memory`, `env` (only the variables the run would add or override, never the inherited environment), `argv` (`<provider>`, then `--settings <settings>` as tokens when attached, then the provider's arguments exactly as given), `provider` (the file the real form would exec, or null), `notebook_route`, `reason` and `unproven` (the list below, which names what the proofs must show and does not track them; which hash passed is in the status line above). The reason is fixed text: it names no key, person, role, note, room or session, and paths in it are written as `<room>` and `<notebook>`. A session identifier appears only inside `argv`, where the provider's own arguments carry it. Exit 0 for every branch.

**Native proof still needed before any real use** (Part B of `packet-claudine-w5-wiring`, a separate named operation under PoT 6.1.5, by the procedure in that case, on the final wrapper, with the Auditor's review and the operator's named go naming its hash; then the launch setting, a Control go, the Session Continuity Manager first, PoT 6.1.2 and 6.1.6):
1. The provider executable the real run would exec, and that the exec passes every argument, the standard streams and the exit status through unchanged.
2. The route that points the provider at the attached notebook: a `--settings` file naming the folder (`autoMemoryDirectory`, as the design measured on 2026-10-31), an environment variable, or another provider-documented route; and that the provider then loads that folder's `MEMORY.md` and writes its memory there.
3. That `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` turns auto memory off for that run in the installed provider.
4. That every launch path of the plugin (a new chat, a resume, a continue, a fork) passes its session as `--resume` or `--session-id`, as measured for one resident on 2026-10-31.
5. The modes the provider gives files it writes in the notebook (George's F2: unknown).
6. That the interpreter line (`/usr/bin/env -S python3 -I -B`) resolves in the plugin's launch environment.
7. That a provider rewrite of the index keeps the projected block at line 1; `project` refuses a block that does not start there.
8. That the route and the load limits measured on 2026-10-31 (200 lines and 25 KB of `MEMORY.md`) still hold on the installed provider.
9. Whether the provider changes the frontmatter of notes copied into a notebook.
10. That an unwired row passes through byte-identical on the real provider.
11. That no arguments runs, inside the room and outside it.
12. That a broken list turns auto memory off for a row of this room.
13. That the plugin's own launch form passes through the wrapper at `bypassPermissions` on a synthetic wired row: stream-json both ways, `--verbose`, `--permission-prompt-tool stdio`, `TERM=dumb` and `CI=true`.

## Recovery and limits

- **Recovery.** The wrapper changes no setting. Its only writes are the settings file and the decision log above; removing that folder loses the log's history and nothing else, because the next launch writes both again. Removing a key from the wired list, or the list itself, returns that row to the provider's default at its next launch; its notebook stays. Removing the wrapper removes the slice. What a live session does if its settings file is removed under it is untested.
- **A carried `--settings`.** A launch that already gives the provider `--settings` gets auto memory off and no route, because the provider documents no rule for two such flags and a lost route would silently mean the default shared folder. The plugin's chat launches pass none, as proof 4 recorded on 2026-11-07, so this path should not arise for a resident. Its configuration probe carries its own and names no session, so that is the new branch. If it does, the run itself says nothing: the decision log records it, and `--dry-run` states it to whoever asks.
- **A lost notebook tells nobody at the launch.** A resident whose notebook is off for any reason (the index drifting from 0600, a broken registry, a carried `--settings`) wakes without notes, and the wrapper says nothing to the run. The decision log is the only record. Part C's signal is a health leg in `myself.py`, its own pull request, read by the resident at its wake; until that merges, nothing reads the log. If the log itself cannot be written, nothing records that either, because the launch must still run.
- **A broken registry** turns auto memory off for every launch inside this room: its registered residents, wired or not, and any new conversation here. So "unchanged" for an unwired row holds only while the registry and the working directory are healthy. Launches outside this room are decided first and pass through, so it does not reach the residents of other rooms in their own rooms.
- **A session of this room launched from outside it** passes through and gets that place's default memory, where before this slice it would have got its notebook. The log records `outside-the-room` with a null key, because the outside path reads no registry; that is the price of a broken registry not reaching other rooms.
- **The launch setting's reach.** Read in the plugin's code (claude-code-gui 0.35.3, `backend.mjs` 9c5f2e4b1fca73ee), not observed: `cliPath` has two scopes, the global file and `<working folder>/.claude-code-gui/settings.json`, the exact folder with no walk upward, merged over it at every launch. Part C proposes the room's file and no global change. **That is room scope with two leaks, not a seal.** The plugin holds one value, applied by every chat start and every provider command, the `--version` and `--help` probes among them with no working folder and so the global value, and three awaits stand between the set and the spawn. So a launch here can reach the provider directly, with the default slot and no log row, and a launch elsewhere can reach this wrapper, which passes it through as `outside-the-room` with one row. And the terminal action runs whichever value was last applied, so a terminal opened from another room can reach this wrapper with no arguments, which is one reason no arguments is not refused. The plugin can also write that file (line 31364), so one key there is not durable; more than one key is a stop in Part C. At the global scope every Claude launch on the host would pay the wrapper's start-up (medians of 15 runs against a do-nothing fake provider on this host, 2026-11-05: 0.10 seconds outside this room, 0.18 seconds with a notebook attached) and add one line to this room's log, and a wrapper or interpreter that cannot start would stop launches everywhere. At room scope that reach is this room's, leaks aside. The setting takes PoT 6.1.2's review and a named go, and Part C records what Control hears.
- **The plugin's launch forms,** read at that same hash, not observed. A new chat starts with `--session-id`, a later start with `--resume`; neither `--continue` nor `--fork-session` occurs; a fork copies the transcript to a new identifier. So a new chat or a fork in this room names a session the registry does not hold: unregistered, auto memory off. 17 forms share the one command. Five name a session: the chat, title, rename, `/context` and rewind, each decided as that row. Twelve name none: `/usage`, the commit message, the configuration probe, two provider probes, `--help`, `--version`, `auth status`, `auth login`, `mcp`, `agents` and update, each the new branch inside this room. So helper launches outnumber wakes, a row is not a wake, and `new` rows are normal. A change of permission mode, effort or thinking display restarts a live chat, so the next launch is not only an IDE restart.
- **Routes the setting never reaches.** The launcher's `serve` runs the provider directly with `--bg --resume`, by the Auditor's reading of `serve_command`. A `claude` typed in a terminal and the official Anthropic plugin do not read this setting either. A wired resident started by any of these gets the default slot and no notebook.
- **A live merge.** With the setting live, a merge to `main` that touches this wrapper or `mind.py` is in force at the next launch, because the setting names the room's working tree.
- **The bare form and the wrapper's option names.** A first argument equal to `--dry-run`, `--room`, `--registry` or `--provider` is read as the wrapper's, so the bare form cannot carry one first. No provider launch begins with those names, and the plugin's live command line does not, so the plugin cannot reach them by accident.
- **A session started inside another session.** The provider treats it differently: it reads `CLAUDECODE` and `CLAUDE_CODE_CHILD_SESSION` from the environment, its documentation says the `/memory` toggle turns auto memory off but does not turn it back on in such a session, gives `CLAUDE_CODE_DISABLE_AUTO_MEMORY` no scope, and its own text says such a session may not be saved. A resident who runs this wrapper from inside another session gets that difference, because the wrapper passes the environment through. Any proof of this wrapper runs under a clean environment, after a positive control.
- **An inherited switch.** On an attached launch an inherited `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1` is left as it is, so auto memory stays off for that run.
- **Tests and harnesses.** A test or harness that runs the wrapper must never carry a real provider on PATH: the test module removes any folder holding a `claude` and keeps only a tripwire there, after a mutation check on 2026-11-05 started the real provider through tests that inherited PATH.
- **Residents of another room** pass through untouched (the registered-elsewhere branch). On this host, 10 of the registry's 13 Claude rows are registered to another room (counted 2026-11-07, values not read out); a launch path pointed at this wrapper for every Claude launch leaves their present notebooks as they are. The wrapper gives such a run no notebook of this room's home, even when a folder of that key exists here.
- **The working directory is the launch's.** A later change of directory inside the provider is not seen. With no `PWD`, a link cannot be told from the place it resolves to, and the resolved path decides. Measured 2026-11-07 on the plugin's 3 live launches in this room: the working directory equals the room, and `PWD` names another place, which by reading is the plugin backend's own, so it is ignored and the link case cannot fire on the chat path. The terminal action's shell sets `PWD` itself, so the link case can fire there.
- **The argument scan** knows only the documented session flags. A positional argument that happens to look like one of them would be read as one; at worst a run then names an unregistered session and runs with auto memory off.
- **No seam detection.** Like the mind tool, the wrapper cannot see whether another writer holds the notebook.
- **Not in this slice:** seeding a notebook, writing the wired list or the plugin's setting, any change to the plugin's launch path, and the signal.

## Anecdotal Anchor

On 2026-10-31 the Control notebook, 56 notes mostly the Session Continuity Manager's, loaded for three other residents, and the Sessions notebook slot was empty, so its owner woke without his notes. On 2026-11-05 the Sessions slot held five notes written from more than one session, loading for every Claude conversation opened in the room. The notebook was choosing the reader before the registry could. This wrapper reverses the order: registry first, then the notebook, and no notebook at all when the registry cannot answer.

## Integrity Filter Warnings

- A dry run is not a launch. Passing tests prove the decision and the exec on synthetic registries and rooms with a fake provider, not that any real provider loads a notebook.
- `notebook: attached` means the folder passed every check, not that the provider reads it; the route is unproven until the native proof above.
- The decision log records what the wrapper decided, not what the provider then did.
- The wrapper reads the registry. It must never print a registry value or a session identifier outside the passed-through arguments; the tests check every branch for that.

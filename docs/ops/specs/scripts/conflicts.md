## First Principles Rationale

Ported legacy tool. Its docstring opened on the port: "Detect the active-writer condition that can hang a chat on "Initializing"." (the file names no author; attributed to the file). It reports now rather than detects: a reading can show a holder and cannot clear one, so no exit status and no empty list authorizes a resume, a takeover or a write. The earliest receipt that names it is `Receipts/full-codex-rotation-and-relabel-20260808.md` (2026-08-08); 1 receipt(s) name it in all.

## Mechanics and Sequencing

1. `Scripts/check_codex_thread_writer_conflicts.py` (sha256 `39ea9e0ad4a439927b66f20984d697e72bb094b38d194eb0fe5e1cf4928a55e9`) was copied to `ops/lib/scripts/conflicts.py` on 2026-11-01 with 0 edit(s). The correction of 2026-11-07 is the only change since.
2. Command line: `python3 -I -B ops/lib/scripts/conflicts.py [--json]`.
   - Text exits 1 when any finding has `blocks_editor`, and 0 otherwise.
   - `--json` prints the whole reading and exits 0 whatever it finds. A reader takes its answer from the fields.
3. Reads: the process table; the file descriptors of every process it may read; the kernel's lock table, `/proc/locks`; the lock folder and state database of one Codex home; the registry. The home is `CODEX_HOME` when set and not empty, and `~/.codex` otherwise, the provider's own rule. It writes nothing.
4. One finding per lock file named for a thread, whatever the number of holders. Its fields:
   - `thread`, `resident`, `room`.
   - `holders`, each `{pid, kind}`, every process seen holding the file open; `holder_count`, how many. A process with two descriptors is one holder. A descriptor is read when its link names the lock folder or equals a listed lock's resolved path, so a folder or file symlinked to another name stays seen. Identity is the descriptor's device and inode; the link's text is the fallback only when the descriptor cannot be followed.
   - `holder_pid`, `holder_kind`: the first holder, in the order the port read them, processes running a Codex executable first. `holder_kind` with no holder is `gone` when `holder_state` is `stale`, and `unknown` otherwise.
   - `kernel_lock`: `locked`, `not-locked`, or `unknown`, which means the table could not be read, a row in it could not be parsed, or the same inode stands there under another device number. `kernel_lock_pids`: the pids the table names, which can differ from `holders` after a fork.
   - `holder_state`: `held` (a visible holder, the lock confirmed or the table unread); `open-not-locked` (a visible holder, and the table shows no lock); `held-unseen` (no visible holder, and the table shows a lock); `stale` (no visible holder, and the table shows none); `unknown` (no visible holder, and the table gives no answer).
   - `blocks_editor`: any holder other than an editor bridge, or `held-unseen`, or `unknown`. It means an editor is not the holder, and it does not mean an editor can open the thread.
   - `blocks_other_writer`: every state but `stale`. An editor bridge is here: that chat is open in one editor, and any second window, server or client that tries to write it is refused.
   - `stale`: `holder_state` is `stale`, and that alone. Before the correction it meant no visible holder.
5. The whole reading also carries `limit`, the sentence the text prints first, and `coverage`: `codex_home`, `home_source`, `processes_unreadable`, `fd_tables_unreadable`, `lock_table_read`, `lock_files_skipped` (a lock file with no thread in its name), `lock_fds_other_home`, `lock_fds_unlisted` (a descriptor under this home on no listed file, such as a replaced or deleted one).
6. The janitor reads `thread` and `holder_kind`, and the relay design reads `thread`, `holder_pid` and `holder_kind`. Against the port on one state, the 7 fields the port wrote differ in these cases only: no visible holder with no confirmation from the table, where `holder_kind` is `unknown` and `blocks_editor` is true, and `gone` and false before; a second holder that blocks, where `blocks_editor` is true, and false before; a link whose text equals the lock's path while its inode differs, which holds nothing now and held it before; a link reaching the same inode by another path, which holds it now and held nothing before. Each of the last two needs another mount or mount namespace, since on one namespace a link shows the resolved path, a replaced file reads as no holder before and now, and a symlink resolves to the path listed. The janitor acts only on `background-daemon`, so of these it sees only the last two, each more nearly true than before. If the last ever came true for a daemon, a restart would not release a holder outside the service, so the janitor would restart it at every pass meeting its idle rule and warn each time; it does not escalate.

## Integrity Filter Warnings

- Refusal and read-only statements in the docstring: "Writer-conflict success therefore rules out one failure class; it does not prove that a session body will resume." "A reading shows a holder; it never clears one." "It changes nothing."
- Limits that stand after the correction. It is one moment's reading, so a holder can come or go in the next instant. It reads one home, and only counts a lock descriptor it sees in another. A refused process or descriptor table is a count; the kernel's table still covers it, unless the reader stands in another PID namespace, which sees less of that table. `locked` rests on the provider taking the lock with `File::try_lock`, by that Contractor's source read at `rust-v0.165.0` and `rust-v0.167.0`, and a later provider could lock otherwise. The executable behind a holder is not reported: the IDE's adapter bundles 0.165.0 and the PATH CLI is 0.167.0.
